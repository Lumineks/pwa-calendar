# Journal Calendar — Project Context

This file is the canonical context for AI agents working on this project. It captures the assignment, locked-in decisions, and the rationale behind them so future sessions don't need to re-derive any of it. Read this first; only consult the deeper analysis canvases (see "References") when you need full reasoning.

## Project Summary

A simple iOS-only weekly journal/calendar app, modeled after the "План недели – Ежедневник" app. The look-and-feel is a paper school journal: lined pages, a spiral binding down the middle, day tabs sticking out from the page. Users tap a day to expand it to a full-screen note editor.

Intended audience: a single user (the project owner's friend). Not a product, not multi-user. The same user may use the app across multiple devices (e.g. iPhone + iPad) and they share the same data via a pre-shared access code. No traditional auth flow, no accounts, no email.

## Functional Scope

**In scope (must-have):**
- Weekly calendar view styled as a paper journal (lined pages, spiral binding, day tabs).
- Month selector / navigation.
- Plain-text note editing on the lines of any specific day.
- Per-day full-screen view for more writing space.
- Local persistence per device via IndexedDB (canonical store on each device, works fully offline).
- Remote persistence: every change is synced in the background to a Cloudflare Worker + KV store.
- Multi-device data sharing: pasting the same access code on a second device shows the same journal.
- One-time access-code entry screen on first launch of each device.
- Manual one-tap "Back up" that exports a JSON file via the iOS Share Sheet (kept as a secondary safety net even though remote sync provides primary durability).

**Out of scope (explicitly rejected):**
- Real authentication (passwords, email, OAuth, SMS).
- Real-time / collaborative editing. Periodic pull/push is enough.
- Multi-user (still single user; multi-device is for that one user only).
- Notifications / reminders.
- UI customization or themes.
- Multi-language / i18n. UI labels are Russian only.
- Android support.
- Recurring events, categories, task checkboxes (these exist in the reference app but are not wanted here).
- CRDT-based conflict resolution. Last-write-wins per entry is the chosen strategy.
- Self-service token rotation. The project owner rotates and re-shares manually if needed.

**Future-friendly but not v1:**
- Rich text editing. Plain text is fine for v1, but the data model and editor choice should leave room to swap in a rich-text editor (e.g. Tiptap) later without a rewrite.

## Locked-In Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Distribution | **PWA, installed via Safari "Add to Home Screen"** | Zero re-install friction without a $99/yr Apple Developer account. Every native iOS path requires re-signing every 7 days under free provisioning. |
| Apple Developer account | **None** | User chose the free path. This rules out TestFlight, Ad-Hoc, and App Store distribution. |
| Frontend framework | **Svelte 5 + Vite + TypeScript** | User wanted to learn something new beyond their React + Vite background. Svelte 5 (with runes) gives the smallest amount of ceremony, scoped CSS by default, and built-in transitions for the day-tab → fullscreen expand effect. Excellent fit for a weekend-scope, small-app PWA. |
| Routing | **`svelte-routing`** | Small, popular, sufficient for the three screens (TokenGate, Week, Day). Hash-based or history-based nav both work. Don't reach for SvelteKit — its server-rendering features are wasted on a static GH Pages SPA. |
| Styling | **Tailwind CSS layered on Svelte's scoped `<style>`** | Tailwind utilities for layout/spacing; Svelte's per-component scoped styles handle the paper/notebook visuals locally (lined-paper backgrounds, spiral binding, day-tab shapes) without CSS modules or styled-components. |
| PWA tooling | **`vite-plugin-pwa` (Workbox under the hood)** | Generates the service worker and the web manifest. Works the same with Svelte as with React. |
| Local storage | **IndexedDB via Dexie**, keyed by ISO date `YYYY-MM-DD` | Source of truth on each device. Durable on installed iOS PWAs (iOS 16.4+). One table `entries`, value is `{ body: string, updatedAt: ISOString }`. Debounced auto-save on edit (~300 ms). |
| Remote persistence | **Cloudflare Worker + KV namespace** | Matches the user's pre-shared bearer-token model exactly. Worker holds the secret; the frontend ships only the public Worker URL. Free tier is effectively infinite for one user. ~50 lines of TypeScript total. |
| Auth model | **Pre-shared bearer token (project-owner-generated)** | Worker compares the `Authorization: Bearer <token>` header to a `JOURNAL_TOKEN` env var with a constant-time comparison. Token is generated by the project owner with `crypto.randomUUID()`, sent to the friend over Signal/iMessage, pasted into the app once per device, and stored in `localStorage`. |
| Sync model | **Local-first; remote is an eventual mirror** | Every edit goes to IndexedDB first (UI is instant, works offline). A debounced job (~3 s idle) pushes a "dirty set" of changed entry keys to the Worker. Periodic pull on launch and every few minutes when online. Conflict resolution: latest `updatedAt` wins per entry. |
| Backup strategy | **Remote sync is primary; manual JSON export is the secondary safety net** | The "Back up" button still exports a JSON via the Share Sheet, kept as belt-and-suspenders against the friend losing the access code or against a Worker outage. |
| Hosting | **GitHub Pages**, default `*.github.io` URL | User explicitly accepted. Free, auto-deploys from a branch. No custom domain. |
| UI language | **Russian** | Reference app is Russian/Ukrainian; user's friend uses Russian. All visible strings hardcoded in Russian. No i18n framework. |
| Visual fidelity target | **"Same spirit, simpler aesthetic"** | Lined paper, spiral, weekday tabs — yes. Watercolor seasonal background, hand-drawn fonts, custom textures — skip for v1. |
| Date math | **`date-fns`** with `date-fns/locale/ru` for weekday/month names | Lightweight, tree-shakeable. |

```
 data/

public/

 icon-192.png

worker/

 index.ts # Cloudflare Worker entry: routes + bearer-token check + CORS

```

### Worker API surface

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Returns 200 if the bearer token matches, 401 otherwise. Used by the TokenGate to validate. |
| GET | `/entries` | Returns the index of dates that have entries (and optionally a date range of full entries). Used on app launch and during periodic refresh. |
| GET | `/entries/:date` | Single entry fetch, used when opening DayView. |
| PUT | `/entries/:date` | Upsert one entry. Body: `{ body, updatedAt }`. |
| DELETE | `/entries/:date` | Delete one entry. |
| GET | `/export` | Returns the entire dataset as one JSON. Powers the manual backup button. |

### KV shape

Single namespace `JOURNAL`. Keys: `entries:YYYY-MM-DD`, values: `{ body: string, updatedAt: ISOString }`. Optional summary key `index` listing the dates that have entries (lets the weekly view render without a `list` operation across the whole namespace).

### CORS

The Worker allowlists exactly the GitHub Pages origin (e.g. `https://<user>.github.io`). No wildcards. Preflights cached for a day.

On iOS 15 or below the PWA experience degrades meaningfully (storage may be evicted, fewer manifest features). Fallback if this becomes a problem: revisit Path B (Capacitor + TestFlight, $99/yr) — same React/TS code wraps in an afternoon.
2. **Russian UI copy.** Final wording for menus, the Back-up button, the day-view header, the TokenGate screen, and onboarding strings has not been chosen. Use literal translations of the reference app's labels as a starting point. Suggested for TokenGate: heading "Введите код доступа", action "Сохранить", error "Неверный код".
3. **Onboarding install instructions.** A first-visit page should walk the friend through "Tap Share → Add to Home Screen" with a screenshot, since this isn't a step Russian-speaking iOS users see often.
4. **Cloudflare account & token generation.** Project owner needs to: create a free Cloudflare account, run `wrangler init` for the worker, create the KV namespace, set `JOURNAL_TOKEN` via `wrangler secret put`, deploy, then send the token to the friend over a private channel.
5. **Token-rotation procedure.** If the token is ever leaked or suspected compromised, the owner rotates the env var (`wrangler secret put JOURNAL_TOKEN`) and resends the new token to the friend. She re-pastes it on each device. Document this lightly in the project README when it exists.

## Constraint Reasoning (Short)

- **Why not native (SwiftUI / RN / Expo / Capacitor / Flutter)?** All require a signed `.ipa`. Without a $99/yr Apple Developer membership, the only free signing certificate is the personal one issued by Xcode, which expires after 7 days. The user requires zero re-install friction, so every native path is excluded. Capacitor remains a "free upgrade" later: same Svelte + Vite codebase wraps in an afternoon if the user ever pays $99/yr and wants iCloud Drive container backup.
- **Why not AltStore / SideStore / TrollStore?** They work around the 7-day limit but require either a server, a Mac running 24/7, occasional manual re-pairing, or an iOS-version-dependent exploit. Too fragile for a non-technical friend.
- **Why Svelte over Vue / SolidJS / React?** User wanted to learn something new. Svelte gives the deepest dev-experience shift while still letting a weekend MVP ship: built-in scoped CSS, built-in transitions, smallest output, runes-based reactivity. Vue was the runner-up (largest ecosystem); SolidJS the third (closest JSX, deepest signals model). React was excluded because the user already knows it.
- **Why Cloudflare Worker + KV over Supabase / GitHub Gist?** Pattern matches the user's pre-shared bearer-token mental model exactly. ~50 LOC of Worker code, no email-link auth flow, no off-label use of git providers. Supabase was the runner-up (zero-backend, magic-link auth) and remains a viable swap. GitHub Gist was rejected as feeling off-label for something the friend depends on for months.
- **Why GitHub Pages over Cloudflare Pages?** User explicitly accepted GitHub Pages; both are free and adequate. No reason to add a second vendor.

## Research Tasks Performed (For Provenance)

These tasks were completed during the research phase. Findings are baked into the decisions above — re-doing them isn't necessary.

1. Reviewed the reference app's App Store listing (functionality, IAP model, supported iOS versions, recent changelog).
2. Surveyed iOS distribution mechanisms: App Store, TestFlight, Ad-Hoc, Free Provisioning (Xcode personal account, 7-day cert), AltStore / SideStore, TrollStore, Apple Developer Enterprise. Verified each method's lifetime, cost, and end-user friction.
3. Surveyed candidate stacks for the original commit-to-React decision: PWA (Vite + React/Vue), Capacitor / Ionic, React Native / Expo, SwiftUI, Flutter, Tauri Mobile. Evaluated each on free-distribution feasibility, fit with JS/TS skills, effort, and iCloud backup capability.
4. Researched iOS PWA capabilities and limits (iOS 16.4+ improvements: home-screen install, IndexedDB durability for installed PWAs, Web Share API). Confirmed there is no API for direct iCloud Drive writes from a PWA.
5. Compared backup approaches: IndexedDB-only, manual export via Share Sheet, third-party sync (gist / Cloudflare KV), Capacitor `Filesystem` to iCloud container, native CloudKit.
6. **Frontend framework deep-dive.** Compared Svelte 5, Vue 3, and SolidJS as React alternatives, plus a rejection list (Preact, Qwik, Astro, Angular, Lit, HTMX, Alpine, vanilla web components). Mapped React idioms to each — `useState`, `useMemo`, `useEffect`, conditional/list rendering, two-way binding. Confirmed each works with `vite-plugin-pwa`, Dexie, and static export to GitHub Pages.
7. **Remote persistence deep-dive.** Analyzed three architectural patterns: BaaS with row-level security (Supabase, Firebase, Appwrite), tiny edge function + bearer token (Cloudflare Workers + KV/D1, Deno Deploy + Deno KV, Val Town, Vercel Functions), and Git-as-DB (GitHub Gist + PAT, GitHub repo + PAT). Rejected: direct Postgres/MySQL, Neon/Turso without a gateway, Hasura/Xata, JSONBin/KVdb/Pantry, public-bucket + client-side encryption, CRDT sync (Yjs/Automerge), self-hosted PocketBase/Appwrite. Designed the local-first sync architecture (Dexie as source of truth, debounced push of a dirty-set, periodic pull, last-write-wins by `updatedAt`).
8. Asked the user clarifying questions in three rounds, covering: willingness to pay $99/yr, re-install tolerance, stack preference, visual fidelity, data durability, scope, iOS version, plain vs. rich text, UI language, hosting domain, openness to a non-React framework, and persistence approach including multi-device intent.
