## 4. Critical Findings 🔴

### 🔴-1 — Tiptap bundle is ~95 KB gzip, not 40–60 KB. The spec's alarm threshold is breached on day one.

Spec §2 states «Ожидаемая цена ~40–60 КБ gzip» and §"Открытые допущения" sets an alarm at
«если общий gzip-бандл превысит ~150 КБ … History — первый кандидат на выброс».

Measured, not estimated:

| Configuration | raw (min) | **gzip -9** |
|---|---|---|
| Document + Paragraph + Text + TextStyle + Color + UndoRedo | 311,209 B | **95,480 B** |
| same, minus UndoRedo | 286,299 B | **87,583 B** |
| `new Editor({extensions: []})` — bare `@tiptap/core` + ProseMirror floor | 279,999 B | **86,140 B** |

Current shipped app bundle (`dist/assets/index-B9vGgAOh.js`): 200,282 B raw / **66,264 B gzip**.

Therefore: **66 KB + 95 KB ≈ 161 KB gzip**, over the 150 KB alarm line immediately.

The proposed mitigation does not work. Dropping History/UndoRedo saves **7,897 B gzip (8.3%)**
and lands at ~154 KB — still over. The floor is ProseMirror itself: 86 KB gzip before a single
Tiptap extension is added. **90% of the cost is not removable by trimming extensions.**

Method: `npm i @tiptap/*@3.30.5`; `esbuild src/main.js --bundle --minify --format=esm`; `gzip -9`.
Vite/rolldown may differ by a few percent but not by a factor of two. Full reproduction:
`/private/tmp/claude-501/-Users-user-Desktop-projects-personal-journal-calendar/3f9ca3a0-7d09-474c-8a0a-74038bcb4570/scratchpad/bundletest/`

This is a scoping decision, not an implementation detail — escalated in §8.

### 🔴-2 — `@tiptap/pm` is a required peer dependency and is absent from the spec's dependency list.

`@tiptap/core@3.30.5` declares `peerDependencies: {"@tiptap/pm": "3.30.5"}` — an **exact pin**, not
a range. Same for `@tiptap/extensions`. Every `@tiptap/*` package peer-depends on the others at the
exact same version string.

Consequence: `"^3.30.5"` ranges across several `@tiptap/*` entries in `package.json` will drift
apart on the next `npm install` (Tiptap ships near-daily) and produce `ERESOLVE` peer conflicts.

Constraint: pin all `@tiptap/*` to one identical exact version, and add `@tiptap/pm` explicitly.

### 🔴-3 — The multi-token `verifyToken` loop as specified will throw or leak token length.

Spec §1 requires iterating **all** entries of the `JOURNAL_TOKENS` map with a constant-time compare
of each, «без раннего выхода».

`crypto.subtle.timingSafeEqual` **throws** when the two buffers differ in byte length
(confirmed: Cloudflare Workers Web Crypto docs; matches the existing comment at
`worker/src/index.ts:37`). A map of tokens will contain tokens of differing lengths, so a naive
loop throws on the first length mismatch.

The current code (`worker/src/index.ts:38`) guards with `if (a.byteLength !== b.byteLength) return false;`
— which is exactly the early return that leaks the secret's length through response timing, and
which the spec's «без раннего выхода» language is trying to avoid.

Cloudflare's documented pattern for the mismatch case:

```ts
const lengthsMatch = userValue.byteLength === secretValue.byteLength;
const isEqual = lengthsMatch
  ? crypto.subtle.timingSafeEqual(userValue, secretValue)
  : !crypto.subtle.timingSafeEqual(userValue, userValue);   // always false, constant time
```

Source: <https://developers.cloudflare.com/workers/examples/protect-against-timing-attacks/>

Note this still leaks *whether* lengths matched via the branch. For a map of N tokens the cleaner
construction is to SHA-256 both sides first and `timingSafeEqual` the two fixed-32-byte digests —
lengths are then always equal, the throw is unreachable, and no branch exists. Either is
defensible; the plan must pick one explicitly rather than inherit the v1 early return.

## 5. High-Priority Findings 🟠

### 🟠-1 — `@cloudflare/vitest-pool-workers` was renamed. Use `@cloudflare/vitest-plugin`.

Cloudflare renamed the package on **2026-08-19** (changelog:
<https://developers.cloudflare.com/changelog/post/2026-08-19-vitest-plugin/>).
`@cloudflare/vitest-plugin@1.1.0` (2026-08-25) is v1 of what was `@cloudflare/vitest-pool-workers@0.22.0`.
The old name is not yet npm-`deprecated` but is superseded; writing new tests against it in
August 2026 means writing them against a renamed package.

Answering the spec's actual question — **plain vitest with a hand-mocked `KVNamespace` vs. the
Workers pool** — for this worker the pool wins, and not marginally:

- The worker's whole contract is KV semantics (`list` with prefix, `get`/`put`/`delete`,
  eventual-consistency behaviour) plus `crypto.subtle.timingSafeEqual`. **`timingSafeEqual` is a
  workerd-only non-standard extension — it does not exist in Node.** A hand-mocked test of
  `verifyToken` under plain vitest cannot execute the real function at all; it would test a stub.
  That is the single most security-sensitive function in the v2 release (§1 multi-account isolation).
- Spec §6 explicitly wants prefix-isolation tests (`a:test:*` invisible from `a:marina-actress:*`).
  Those are KV `list({prefix})` semantics; a hand mock tests the mock.
- Spec §6 already plans «прогон на локальном miniflare-KV перед продом» — the plugin *is* miniflare,
  so this removes a separate tool rather than adding one.

Version compatibility with the repo:
- `@cloudflare/vitest-plugin@1.1.0` peers: `vitest ^4.1.0`, `@vitest/runner ^4.1.0`, `@vitest/snapshot ^4.1.0`.
- It **bundles** `wrangler 4.126.0` + `miniflare 5.20260825.0-alpha` as direct dependencies.
- `worker/package.json` has `wrangler ^4.90.1`, which resolves to 4.126.0 — **compatible, no bump needed**,
  though npm will hoist/dedupe to whatever the plugin pins.
- `configPath` accepts `.toml` — the existing `worker/wrangler.toml` works as-is, no jsonc conversion.
- `worker/wrangler.toml` has `compatibility_date = "2026-05-01"`, which is honoured by the test runtime.

Migration codemod exists: `npx @cloudflare/codemods vitest:pool-workers-to-vitest-plugin`
(not needed here — there are no existing tests).

### 🟠-2 — Open, unfixed iOS Safari freeze in Tiptap 3 triggered by text selection.

`ueberdosis/tiptap#7514` — "[iOS/iPad Safari] Editor causes global page freeze", **open**, filed
2026-02-10, affects Tiptap 3.x, no maintainer fix. Symptom: after text selection in the editor,
all `click` events **outside** the editor stop firing globally; `:hover` sticks on `<html>`;
`touchstart`/`touchend` still work; persists after the editor unmounts; only a reload recovers.

This lands directly on spec §2's primary interaction: «тап с выделением — красит выделенный
фрагмент». Selection-then-tap-a-color-dot is the exact sequence reported. The reporter notes
"a single normal text selection already caused their page to freeze" for some users.

Known partial workaround from the thread: bind `touchend` instead of `click`. The failed
workarounds were removing listeners and `window.getSelection().removeAllRanges()`.

Related open iOS issues in the same release line, lower impact for this spec:
- `#7540` — keyboard ▲/▼ navigation ignores Tiptap editors (3.20.0).
- `#2629` — caret/selection visible outside the scroll clip in `overflow-y: auto` contenteditable.
  This one interacts with spec §4's B7 change (`.preview` → `overflow-y: auto`) and with the
  editor's own scroll container.

### 🟠-3 — `crypto.subtle` is `undefined` when the iPhone hits the Vite dev server over a LAN IP.

Spec §1 makes `sha256(token)` the **namespace key** for the Dexie DB name and every localStorage
key. Spec §7 Phase C requires «смоук на реальном iPhone».

`crypto.subtle` is gated on secure context. `http://localhost:5173` and `http://127.0.0.1:5173`
**are** secure contexts. `http://192.168.x.x:5173` — what `vite --host` serves to a phone on the
same Wi-Fi — **is not**. `crypto.subtle` is `undefined` there, on iOS Safari as on every browser.

Concrete failure: the namespacing helper throws → no DB name → app dead on the phone in dev, while
working perfectly on the laptop. This will read as a Tiptap or Dexie bug and burn debugging time.

Not a production issue: GitHub Pages is HTTPS. It is a dev-loop issue on exactly the device the
spec designates for acceptance testing.

Options for the plan (pick one): run dev over HTTPS with a local cert (`@vitejs/plugin-basic-ssl`);
or tunnel; or make the hash helper synchronous and dependency-free (a small non-crypto digest is
sufficient — this hash is a *namespace discriminator*, not a security boundary; the security
boundary is the worker's token check plus the KV prefix, per spec §1).

That last point is worth stating plainly: the spec's isolation guarantee («Вход тестовым токеном
… не может ни увидеть, ни запушить данные marina-actress») rests on the **worker**, not on the
client-side hash. The hash only needs collision-resistance across two known tokens. Using
`crypto.subtle` for it buys nothing and costs the secure-context constraint.

## 6. Medium Findings 🟡

### 🟡-1 — Node 18 in the current shell cannot build this repo.

`node -v` → `v18.20.8` (nvm default). Vite 8's rolldown requires `node:util.styleText` →
`SyntaxError: The requested module 'node:util' does not provide an export named 'styleText'`.
Vite 8 declares `@types/node ^20.19.0 || >=22.12.0`. Node 20.19.0, 22.21.1, 24.16.0 and 25.4.0
are all installed under nvm. Not caused by v2, but the v2 work adds a test runner and a build-time
asset generator, both of which will hit this. An `.nvmrc` / `engines` field would fix it once.

### 🟡-2 — `pwa-asset-generator` is healthy, but note what 8.1.5 actually depends on.

Not abandoned: releases 8.1.3 (2026-03-12), 8.1.4 (2026-03-14), **8.1.5 (2026-06-01)**; the 8.1.5
commit is `fix(puppets): update apple scraper` — i.e. the maintainer is still tracking Apple's
device-size list. Repo not archived.

Dependencies shifted: 8.x uses `puppeteer-core@^24` + `chrome-launcher@^1.2.1`, **not** full
`puppeteer`. It launches a **locally installed Chrome** rather than downloading Chromium.
CI or a machine without Chrome will fail. `engines: node >= 18`.

`apple-touch-startup-image` is still required in 2026 — iOS/iPadOS still do not generate launch
screens from the Web App Manifest; per-device `<link rel="apple-touch-startup-image" media="...">`
remains the only mechanism. Spec §5's approach is correct.

Current flags (8.1.5): `--splash-only`, `--background`, `--index`, `--path`, `--dark-mode`.
Shape:

```
npx pwa-asset-generator public/icon-512.png ./public \
  --splash-only --background "#fbf6e9" --index ./index.html --path "%PUBLIC_URL%"
```

Two cautions for the plan:
- `--path` must be set for this repo's **GitHub Pages subpath** deploy. The v1 audit already
  fixed `navigate()` calls for `BASE_URL` (commit 0a3dc1c); generated `href`s have the identical
  hazard and the generator will emit root-relative paths by default.
- The full Apple splash set is ~30 PNGs and runs to several MB. Spec §5 says they «войдут в
  precache» via `vite-plugin-pwa`. Workbox's default `maximumFileSizeToCacheInBytes` is 2 MiB
  per file (fine per-image) but the **total** precache manifest will grow substantially. Verify
  the generated precache size rather than assuming.

### 🟡-3 — `TextStyleKit` is the lighter-config alternative to wiring TextStyle + Color separately.

`@tiptap/extension-text-style@3.30.5` exports `TextStyleKit`, which registers textStyle +
color + backgroundColor + fontFamily + fontSize + lineHeight, each switchable off:

```ts
TextStyleKit.configure({
  backgroundColor: false, fontFamily: false, fontSize: false, lineHeight: false,
})
```

Not a saving over importing `{ TextStyle, Color }` directly (same module, tree-shaken either way)
— listed only so the plan doesn't rediscover it. Direct named imports are clearer here.

### 🟡-4 — `svelte-tiptap` is not needed and should not be added.

`svelte-tiptap@3.0.1` (2025-10-28) does support Tiptap 3 + Svelte 5, but its peer set is
`@tiptap/extension-bubble-menu` + `@tiptap/extension-floating-menu` + `@floating-ui/dom` —
all of which the spec explicitly does not want (the palette is «ряд цветных точек в шапке DayView»,
not a bubble menu). Its npm description still reads "Svelte components for tiptap v2".

Tiptap publishes **no** official Svelte package. The official Svelte guide
(<https://tiptap.dev/docs/editor/getting-started/install/svelte>) now covers Svelte 5 runes and
recommends `@tiptap/core` directly. Recommended shape: hold `let editorState = $state({ editor: null })`
and reassign it from `onTransaction` to force re-render — reassignment, not mutation, because the
`Editor` instance is not deeply reactive and mutating it will not trigger runes. `new Editor(...)`
must be constructed inside `onMount`/`$effect` (it touches `document`).

## 7. Design Constraints for the Plan

**MUST**

- Add `@tiptap/pm` as an explicit dependency. Pin every `@tiptap/*` package to the **same exact
  version** (`3.30.5` at time of audit) — peer deps are exact-pinned, not ranged.
- Import `UndoRedo` from `@tiptap/extensions`, not `History` from `@tiptap/extension-history`.
- Import `{ TextStyle, Color }` from `@tiptap/extension-text-style`, not `@tiptap/extension-color`.
- Use `@cloudflare/vitest-plugin` (v1.1.0) with `vitest@^4.1.0`. Config via the `cloudflareTest()`
  plugin, not `defineWorkersConfig`. Point `wrangler.configPath` at the existing `worker/wrangler.toml`.
- In worker tests, import `env` from `cloudflare:workers`; `createExecutionContext` /
  `waitOnExecutionContext` from `cloudflare:test`.
- Handle the `timingSafeEqual` length-mismatch case without an early `return false` — either the
  documented `!timingSafeEqual(a, a)` decoy or SHA-256-then-compare-digests. Pick one and comment it.
- Set `--path` on `pwa-asset-generator` to match the GitHub Pages base path.
- Re-measure the gzip bundle in the first build and compare against the 161 KB projection in §4.1.
- Pin a Node version ≥ 20.19 for build and test (`.nvmrc` or `engines`).

**MUST NOT**

- MUST NOT plan around «~40–60 КБ gzip» for Tiptap. The measured figure is 95 KB.
- MUST NOT treat "drop History" as the bundle-size escape hatch — it recovers 8 KB of 95 KB.
- MUST NOT add `svelte-tiptap`, `@tiptap/starter-kit`, or `@tiptap/extension-bubble-menu`.
- MUST NOT rely on `crypto.subtle` being defined when the dev server is reached over a LAN IP.
- MUST NOT treat the client-side token hash as a security boundary — it is a namespace
  discriminator; isolation is enforced by the worker's token map and KV prefix.
- MUST NOT ship the selection-then-color interaction to the iPhone without explicitly exercising
  tiptap#7514 (select text → tap a color dot → tap anything outside the editor → confirm it responds).

## 8. Open Questions for the Human

1. **Tiptap costs ~95 KB gzip, taking the app from 66 KB to ~161 KB — past the spec's own 150 KB
   alarm line, with no meaningful trim available.** The spec's stated fallback (drop History)
   recovers 8 KB. This is a scoping call I cannot make. Live options: accept ~161 KB and delete the
   threshold from the spec; lazy-load the editor so only DayView pays (WeekView preview renders
   sanitized HTML and needs no editor — this looks viable and cheap given the existing route split);
   or drop Tiptap for a `contenteditable` + `document.execCommand`-free custom span-coloring
   implementation, which for a six-colour-only feature is a genuinely smaller surface than 95 KB.

2. **tiptap#7514 (iOS Safari global click freeze after text selection) is open and unfixed, and the
   spec's core interaction is "select text, then tap".** Is this an accept-and-workaround (bind the
   colour dots to `touchend`), a blocker for the Tiptap choice at all, or something to reproduce
   on the actual target iPhone before committing? Recommend reproducing first — it is a 20-minute
   test against a Tiptap 3 demo and it may decide question 1.

3. **Dev-loop HTTPS.** Phase C tests on a real iPhone; `crypto.subtle` will be undefined over the
   LAN IP. Preference: add `@vitejs/plugin-basic-ssl` to the dev server, or replace the token hash
   with a non-crypto synchronous digest? The latter is less machinery and loses nothing, given the
   hash is not a security boundary — but it changes spec §1's stated `sha256(token)` design.
