## 3. Domain Constraints the Brainstorm Probably Missed

### A. Auth / worker

**A1 — `crypto.subtle.timingSafeEqual` THROWS on unequal lengths. The spec's "без раннего выхода" is literally uncompilable-into-working-code.** [severity: HIGH — functional bug, not a security nit]

Spec §1: *«verifyToken перебирает все пары карты с constant-time сравнением каждой (crypto.subtle.timingSafeEqual, без раннего выхода)»*.

Cloudflare's non-standard `crypto.subtle.timingSafeEqual` requires equal-length buffers and throws otherwise ([docs](https://developers.cloudflare.com/workers/examples/protect-against-timing-attacks)). The current code already knows this — `worker/src/index.ts:37`: `// timingSafeEqual requires equal-length buffers; bail early to avoid the throw.` Removing that early return without the documented substitute makes *every* request throw as soon as one map token differs in length from the incoming one. The spec's own planned test `verifyToken: другая длина` would exercise exactly this.

MUST use the documented pattern (docs were corrected in response to [#23623](https://github.com/cloudflare/cloudflare-docs/issues/23623)):
```ts
const ok = a.byteLength === b.byteLength
  ? crypto.subtle.timingSafeEqual(a, b)
  : !crypto.subtle.timingSafeEqual(a, a);
```
Doc quote: "Do not return early when the input and secret have different lengths. An early return leaks the length of the secret through response timing."

**A2 — residual timing leak: not worth caring about at this threat level; the throw is.** [severity: informational]
Two accounts, one human user, Cloudflare edge jitter in the tens of ms, no attacker model beyond "someone finds the worker URL". The length oracle is a non-issue here. Adopt the constant-time-length pattern because it is the same number of lines and removes the throw — not because the attack is real. Do not spend plan budget hardening further (no rate limiting, no HMAC tokens) unless the human asks.

**A3 — `JSON.parse(env.JOURNAL_TOKENS)` per request is a single point of total outage.** [severity: MED]
A malformed secret (trailing comma, smart quote pasted from a chat app) turns every request into a 500 and there is **no secret rollback** (see D1). MUST parse once, guarded, and fail **closed with 401**, never 500; MUST validate shape (`accountId` matches `[a-z0-9-]{1,32}`, token length ≥ 24) at parse time and log a distinguishable error.

**A4 — no token recovery / rotation story.** [severity: MED, needs human]
The token is the only credential and lives in exactly one place on the friend's phone (`localStorage`, `src/state/auth.ts`). iOS can drop it (see B1). There is no "resend my token" path and no revocation path other than hand-editing a JSON secret. MUST: record both tokens somewhere durable and out-of-band before Phase A, and document a break-glass procedure.

**A5 — `GET /health` returning `{account}` is a token-validity oracle.** [severity: LOW]
Acceptable, but it means the endpoint must be behind the same auth as everything else and MUST NOT be reachable unauthenticated. Confirm the plan does not keep an unauthenticated `/health` for uptime checks alongside the authenticated one.

**A6 — 64 KB body limit must be measured in bytes, and the 400 must be user-visible.** [severity: MED — data loss]
Russian text is 2 bytes/char in UTF-8, so `body.length` (UTF-16 code units) and `TextEncoder().encode(body).byteLength` differ by ~2× for this user's content. If the worker checks bytes and the client checks characters (or vice versa), the client will happily queue an entry the server permanently rejects. Combined with the dirty-set retry loop in `src/data/sync.ts`, one oversized entry **pins the queue forever and blocks every subsequent sync** — a silent, total data-loss mode.
MUST: byte-length on both sides, same helper; MUST: a 400 removes the entry from the dirty set and surfaces a visible error to the user rather than retrying. (KV's own value ceiling is 25 MiB — [KV limits](https://developers.cloudflare.com/kv/platform/limits/) — so 64 KB is a self-imposed product limit, which is fine; it just needs an escape hatch.)

### B. iOS standalone PWA

**B1 — Safari and the home-screen app have SEPARATE storage. The token does not survive installation.** [severity: HIGH — directly breaks the §5 onboarding flow]

[WebKit b/181849](https://bugs.webkit.org/show_bug.cgi?id=181849) and practitioner writeups ([Netguru](https://www.netguru.com/blog/how-to-share-session-cookie-or-state-between-pwa-in-standalone-mode-and-safari-on-ios), [magicbell 2026](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)) are consistent: localStorage, cookies, IndexedDB and SW registrations are not shared between Safari and standalone mode on iOS.

Spec §5 puts `InstallHint` **over `TokenGate`**. The natural user path is: open link in Safari → hit TokenGate → (maybe) enter token → install → open standalone → **empty TokenGate again**, and a second, independent IndexedDB that will do its own full pull. For a user who has to be told "Поделиться → На экран Домой", being asked for a long opaque token twice is where the flow dies.

MUST: show InstallHint **before/instead of** the token prompt when not standalone, i.e. gate order is `install → token`, not `token (+ hint overlay)`. MUST: tell the user in the hint that the token will be asked once more inside the installed app. MUST NOT store anything meaningful in the Safari-side instance.

Also: removing and re-adding the home-screen icon wipes that instance's storage. Recoverable for entries (KV is truth), **not** recoverable for the token.

**B2 — storage eviction: the 7-day cap does not apply to home-screen apps, but three other wipes do.** [severity: MED]
Home-screen web apps have their own use counter that resets on use, so the Safari 7-day script-writable-storage purge does not hit them ([Apple forums 710157](https://developer.apple.com/forums/thread/710157), [magicbell](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)). What still wipes them: low-disk eviction, "Clear History and Website Data", and deleting the icon. Since KV is source of truth this is survivable **except for the token** (A4) and **except for unsynced dirty entries** (D5).

**B3 — the 24 px edge dead zone is folklore, not a documented constant, and iOS 26 muddied it further.** [severity: HIGH for §3]
There is no published width for the WebKit navigation-gesture edge region, and it is not the same as UIKit's `preferredScreenEdgesDeferringSystemGestures` region. The documented, actually-reliable control is: **`preventDefault()` on `touchstart` suppresses back/forward navigation gestures in iOS Safari 13.4+** ([pqina](https://pqina.nl/blog/blocking-navigation-gestures-on-ios-13-4/)) — and Safari registers `touchstart` as `passive: true` by default, so the listener MUST be added with `{ passive: false }` or the call is a no-op.

Second, the double-navigation failure mode is well documented in Ionic's tracker: the system gesture fires *in addition to* the app's own navigation, producing two back navigations ([#22299](https://github.com/ionic-team/ionic-framework/issues/22299), [#29733](https://github.com/ionic-team/ionic-framework/issues/29733)). There is still no manifest-level opt-out ([w3c/manifest#1041](https://github.com/w3c/manifest/issues/1041), open).

Third, iOS 26 added a right-edge swipe-forward gesture in Safari's Compact layout ([Safari 26 notes](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes), [AppleMagazine](https://applemagazine.com/safari-in-ios-26-a-fresh-look-and-smarter-features/)), so the *right* edge is now as contended as the left. The spec's SwipePager wants both directions.

MUST: treat "the system gesture coexists peacefully with a 24 px inset" as an **unverified assumption with a device test as its acceptance criterion**, not a design premise. MUST: implement suppression via non-passive `touchstart` + `preventDefault` for touches that begin inside the pager, and keep a fallback plan (tap zones / date picker) if the gesture cannot be made reliable on the friend's actual iOS version.

**B4 — does history-based `navigate()` swipe-back work in standalone? Partly, and it is a design decision the spec skipped.** [severity: MED]
Standalone home-screen apps do have back/forward swipe gestures and no visible back button — the gesture is the *only* back affordance. That means:
- If SwipePager pushes a history entry per week/day swipe, a browsing session accumulates dozens of entries and the system gesture replays them in reverse. Usable, but the user's mental model ("edge swipe = previous week") only matches while they have not swiped forward-then-back.
- If `navigate()` replaces rather than pushes, the system gesture does nothing and the app appears to have no back at all.
The spec asserts *«история = предыдущие недели»* without stating which. MUST: state the push/replace policy explicitly, and MUST cap history growth (e.g. replace within a contiguous swipe run, push on discrete navigation like month-picker jumps).

**B5 — install detection must use `navigator.standalone`, not just `matchMedia`.** [severity: LOW-MED]
`matchMedia('(display-mode: standalone)')` works on iOS 13+ but is reported unreliable (breaks in fullscreen, inconsistent) ([web.dev detection](https://web.dev/learn/pwa/detection)). On iOS the canonical signal is `window.navigator.standalone === true`. MUST OR them. MUST NOT rely on UA sniffing as the primary gate — iOS 26 changed home-screen-add defaults, and UA strings for iPadOS report as macOS.

**B6 — 16 px zoom floor applies to contenteditable, and it collides with §4's font change.** [severity: MED]
The 16 px rule is about the **computed rendered** size after transforms, and it applies to ProseMirror/CodeMirror/Slate surfaces exactly as to `<input>` ([CSS-Tricks](https://css-tricks.com/16px-or-larger-text-prevents-ios-form-zoom/), [defensivecss](https://defensivecss.dev/tip/input-zoom-safari/)). §4 swaps Georgia for `-apple-system` and recalibrates the baseline against the ruled lines — if that calibration lands the editor below 16px computed, focusing it zooms the whole standalone viewport, and iOS ignores `user-scalable=no` for accessibility so the meta tag will not save you.
MUST: editor computed `font-size >= 16px` as a hard constraint on the line-rhythm math; if the paper rhythm demands smaller text, use `font-size: 16px; transform: scale(k)` and adjust the line box accordingly.

**B7 — keyboard dismissal + animation is the documented iOS standalone viewport bug, and §3 does exactly that.** [severity: MED-HIGH]
Known bug: after the keyboard dismisses in a standalone PWA, `visualViewport.offsetTop` does not return to 0, leaving `position: fixed` / `sticky` elements misaligned, and the standalone viewport can stay shrunk ([dev.to writeup](https://dev.to/cederhook/fixing-the-ios-standalone-pwa-keyboard-bug-that-shrinks-your-viewport-for-good-63d), [contenteditable lab](https://contenteditable.realerror.com/scenarios/scenario-ios-viewport-keyboard/), [Apple forums 744327](https://developer.apple.com/forums/thread/744327)). Purely-CSS fixes are ineffective; JS `visualViewport` listeners are the standard workaround.
§3 DayView blurs the editor **at gesture start** and then animates a translateX. That runs the panel animation concurrently with keyboard dismissal — the worst case for this bug — and the DayView colour-dot header is the element most likely to be sticky.
MUST: blur, then wait for the viewport to settle (`visualViewport` `resize`/`scroll` quiet period or `focusout` + one rAF) before starting the transform; MUST NOT rely on `100vh` / `position: fixed` for the DayView header; MUST add "swipe away from a focused editor, then check header alignment" to the Phase C checklist.

### C. Tiptap / contenteditable with Russian text

**C1 — Tiptap 3.0.0 has an open iOS Safari bug where repeated text selection kills click handling page-wide.** [severity: HIGH — this is the single most likely functional failure in the release]
[tiptap#7514](https://github.com/ueberdosis/tiptap/issues/7514), reported 2026-02-10, still open: rapid select/deselect in the editor on iOS/iPadOS Safari puts Safari into a stuck "touch gesture in progress" state — click synthesis stops globally, `:hover` sticks on `<html>`, and the freeze survives unmounting the editor. Only a full reload recovers. Reported workaround: use `touchend` instead of `click` handlers.
The v2 colour UX is *literally* "select text → tap a dot", repeated. MUST: bind the palette dots (and every other DayView control) to `pointerup`/`touchend`, not `click`. MUST: reproduce-or-clear this on the friend's iOS version during Phase B on the test account, with a documented fallback (drop selection-painting; keep only "current pen affects subsequent typing") if it reproduces.
This is an issue-tracker finding, not community consensus — treat as "one high-quality open report", not "everyone hits it".

**C2 — never `setContent()` while a composition is in flight.** [severity: HIGH — silent text corruption for a Russian typist]
iOS Safari fires duplicate composition-related `beforeinput`/`input` events, and forcing a DOM update on an event whose `inputType` is null/undefined causes subsequent characters to land in the wrong place and breaks model–DOM sync ([contenteditable lab ce-0584](https://contenteditable.realerror.com/cases/ce-0584-ios-safari-inputtype-null-forced-render-breaks-sync/), [w3c/input-events#86](https://github.com/w3c/input-events/issues/86)). Diacritics/multi-node text can be reordered or split. iOS Russian typing is predictive-text-heavy, so compositions are the normal path, not an edge case.
Spec §"Фикс B1" guards the remote-pull re-read on **focus**. Focus is the wrong guard: a background pull can land while the editor is focused-but-idle *and* mid-composition, and the flush-on-date-change path also writes during typing.
MUST: guard every programmatic content write on `editor.view.composing === false` **and** `!editor.isFocused`; if composing, defer to `compositionend`. MUST: the 300 ms debounce reads `getHTML()` — reading during composition can capture a half-formed word; debounce should also reset on `compositionstart`.

**C3 — `autocorrect` / `autocapitalize` attributes are reported not to take effect on contenteditable in iOS Safari.** [severity: LOW]
So "turn autocorrect off" is not an available mitigation if autocorrect turns out to fight the editor. Plan accordingly; do not put "disable autocorrect" in a fallback list as if it were free.

**C4 — caret visibility in a scrollable contenteditable on iOS.** [severity: LOW-MED]
[tiptap#2629](https://github.com/ueberdosis/tiptap/issues/2629): caret and selection render in the *hidden* part of a scrollable `contenteditable` div on iOS Safari; and the keyboard can cover the line being typed with no auto-scroll. The v2 DayView is a scrollable page with a sticky header + keyboard — add "type near the bottom of a long entry, confirm the caret stays visible" to the device checklist.

**C5 — legacy plain-text detection heuristic is too narrow.** [severity: LOW]
Spec: *«детект: строка не начинается с `<p>`»*. Tiptap `getHTML()` on a document whose first node carries a colour mark still starts with `<p>`, so that direction is safe — but a legacy plain-text entry that happens to start with a literal `<p` (unlikely in a diary, but the sanitizer will have textified pasted HTML into visible angle brackets at some point) would be misclassified and rendered as markup. MUST: store an explicit format marker, or detect via "parses to at least one element node" rather than a prefix string test. Cheap now, unfixable later once entries are ambiguous.

### D. Migration & data safety

**D1 — `wrangler rollback` does NOT roll back secrets, and the spec deletes `JOURNAL_TOKEN` in the same change.** [severity: HIGH — the stated rollback plan does not work]
[Cloudflare rollback docs](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks) / [wrangler rollback reference](https://www.mintlify.com/cloudflare/workers-sdk/commands/rollback): rolling back restores code and does **not** restore secret values; wrangler prompts for extra confirmation when the target version's secrets differ from current ([workers-sdk#5950](https://github.com/cloudflare/workers-sdk/commit/007562109b583adb6ae15bba5f50029735af24e5)).
Spec §1: *«Старый секрет JOURNAL_TOKEN удаляется из worker'а и из wrangler-секретов»*, and §"Откат" step 6 assumes `wrangler rollback` restores a working v1. It does not — the rolled-back v1 code reads `env.JOURNAL_TOKEN`, gets `undefined`, and (depending on the comparison) either 401s everything or, worse, compares against an empty buffer.
MUST: keep `JOURNAL_TOKEN` set as a secret through the entire rollback window; delete it in a separate, later change (suggest ≥ 2 weeks after Phase A smoke passes). MUST: add "rollback rehearsal on the test account" to Phase A — deploy v2, roll back, confirm v1 still authenticates, roll forward.

**D2 — KV is eventually consistent (up to 60 s), which breaks both the verification step and the post-deploy window.** [severity: HIGH — the biggest data-loss risk in the plan, and the spec does not mention consistency at all]
[How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/): changes may take up to 60 seconds or more to become visible at other network locations, and **negative lookups are cached too** — so a freshly-written key can read as *absent* elsewhere for up to a minute.
Consequences for the §1 protocol:
- After step 4 (deploy), the worker may serve `a:marina-actress:index` as **missing** for up to 60 s at the friend's colo. The v2 client sees "index empty" → this is exactly the trigger condition for *«первый syncStart для неймспейса, у которого локальная база пуста»* → it performs a "successful" full pull of **nothing** and presents an empty journal as a correct state.
- If she then writes an entry, a read-modify-write of `a:<acct>:index` against a stale/absent index can persist a one-element index, **losing the date list for every prior entry**. KV has no compare-and-swap; concurrent index RMW loses writes by design.
MUST: the client MUST distinguish "index fetch returned empty" from "index fetch failed" and MUST NOT treat an empty index as a completed initial pull — require an explicit success marker (e.g. worker returns `{index, generation}` or the client requires a non-empty index OR an explicit `"empty": true` flag) before writing the "namespace initialised" flag.
MUST: never rebuild `index` from a client-supplied full list; index mutations must be additive per-date on the server, and the migration must not run concurrently with client writes.
MUST: insert an explicit **quiet window** between step 2 and step 4 (ask the friend not to open the app; verify ≥ 60 s after the last copy write, reading through the *deployed worker*, not the REST API).
SHOULD: consider a `MIGRATING` flag the worker honours by returning 503 for the affected account, so the client backs off instead of concluding "empty".

**D3 — the verification step verifies the copy against itself.** [severity: HIGH — logic hole in the stated protocol]
Spec step 3: *«повторно прочитать оригинал и копию, побайтово сравнить каждое значение»*. If the key set being iterated is the same array the copy step produced, then any key the copy step never saw (missed page of `list()`, key not yet visible due to D2, key present in `index` but never listed) is invisible to verification, and the report cheerfully says "N ключей, N совпадений".
MUST: derive the verification key set **independently** — from `index` (the app-level authoritative date list) — and assert `index.length === copied.length === verified.length`, with the union of `list()`-derived keys and `index`-derived keys as the copy set. Any key in one set but not the other is a hard stop.

**D4 — `list()` pagination.** [severity: MED]
`list()` caps at 1000 keys per page and requires the cursor **and the prefix** on every successive call; `list_complete` is the termination signal ([KV list docs](https://developers.cloudflare.com/kv/api/list-keys/), [community report on prefix+cursor mismatches](https://community.cloudflare.com/t/kv-list-with-prefix-includes-mismatches-when-paginating/516969)). A journal will be under 1000 today, so this will *appear* to work and will silently truncate later. MUST: paginate properly, and MUST assert the count against `index` (D3) so truncation is caught rather than assumed away.

**D5 — the "принятое окно" for the orphaned legacy dirty set is materially underestimated.** [severity: HIGH — this is the one unbounded data-loss path]
Spec: *«Окно исчезающе мало: правки уходят в KV через ~3 с после ввода»*. That is the **online** case. This is an explicitly offline-first app; `src/data/sync.ts` maintains `journal:dirty` and `journal:backoff` in localStorage precisely because writes can sit unsent indefinitely — no signal, airplane mode, or an exhausted backoff after repeated failures. The real window is "however long her longest offline stretch was, plus however long the backoff had grown". Combined with D6 (the new client may not activate for days), it is not a 3-second window.
MUST: on first run in a new namespace, drain the legacy state before declaring the namespace initialised — read the legacy `journal:dirty` map and the legacy `journal` Dexie DB, push any dirty dates into the new account's key space (LWW by `updatedAt`), and only then mark initialised. This is a small, bounded piece of code and it removes the only path that loses content the friend actually wrote.
MUST (at minimum, if the drain is rejected): on first run, if the legacy DB is non-empty and its dirty set is non-empty, show a visible list of the affected dates rather than silently orphaning them.

**D6 — "fresh DB + full pull" requires network on first launch, and the first launch may be days after deploy.** [severity: MED-HIGH — UX-catastrophic, technically "no loss"]
Spec: *«офлайн-первый-запуск даёт пустую базу, которая наполнится при появлении сети — потерь нет»*. Technically true. Experientially, the friend opens her diary and every entry is gone. For the one user this product has, that is the worst possible failure presentation, and it is reachable by simply opening the app in the metro.
Additionally, on iOS a standalone PWA's service worker update typically activates only on a full app restart, so the namespace switch happens whenever her app next cold-starts — not at deploy time. Phase A's smoke test *«подруга ничего не заметила»* therefore cannot be confirmed from the server side at deploy time.
MUST: when the new namespace is empty, the legacy DB is non-empty, and the initial pull has not succeeded, render an explicit "данные загружаются, нужен интернет" state — never an empty journal. MUST: the legacy-drain and the namespace switch must be triggered by client version detection, not assumed to coincide with deploy.

**D7 — the delta step (step 5) needs to be dry-run-first and must never clobber newer data.** [severity: MED]
`updatedAt` is client-set, so clock skew makes "wins by larger updatedAt" non-authoritative. After deploy, writes land in the new key space; a delta script copying legacy→new must be incapable of overwriting a newer new-space value.
MUST: default to report-only; require an explicit `--apply`; log every key it *would* overwrite with both timestamps; hard-stop if any new-space value is newer than its legacy counterpart (that means the direction assumption is wrong).

**D8 — the backup snapshot is plaintext personal diary content, written on a machine with a documented compromise.** [severity: MED — privacy, not correctness]
Repo history: commit `6571752 security: remove injected malware from repo`, and the project memory records malware pushed from a second Windows machine in Aug 2026 that "can recur until that box is cleaned". Spec §1 step 1 says only *«В git не коммитить»*.
MUST: write the snapshot **outside the repository working tree entirely** — a stray `git add -A`, a malicious pre-commit hook, or a build step that globs the project directory should be unable to reach it. `.gitignore` is a courtesy, not a control. SHOULD: encrypt at rest (`age`/`gpg`) and delete the plaintext after the second copy is confirmed.

### E. Sanitization

**E1 — the allowlist design is right; the "sanitize to a string, then set innerHTML" shape is where mXSS lives.** [severity: HIGH — and note v1 had no HTML sink at all, so this is new attack surface]
The HTML spec does not guarantee that serialize-then-reparse round-trips; every historical DOMPurify bypass exploited the gap between the tree the sanitizer inspected and the tree the sink built — namespace confusion via MathML/SVG, `<mglyph>`, `<noscript>`, `<template>` ([DOMPurify attack classes](https://github.com/cure53/DOMPurify/wiki/Attack-Classes-&-Bypass-History), [Securitum mXSS writeup](https://www.securitum.com/mutation-xss-via-mathml-mutation-dompurify-2-0-17-bypass.html), [Google Bug Hunters](https://bughunters.google.com/blog/escaping-and-in-attributes-how-it-helps-protect-against-mutation-xss)).
Concretely, for `src/data/sanitize.ts`:
- MUST insert **nodes**, not a serialized string. Parse with `DOMParser`, prune the tree, then `replaceChildren(...cleanNodes)`. If the WeekView preview uses Svelte `{@html}`, that is a serialize→reparse cycle and needs either the node-insertion path or a stability check (sanitize twice; if pass 1 output ≠ pass 2 output, reject the content).
- MUST explicitly drop namespaced elements (anything whose `namespaceURI` is not XHTML), comment nodes, `<template>` content, `<noscript>`, and `<style>`.
- MUST validate colour via **CSSOM, not string matching**: set the candidate on a detached element, read back `el.style.color`, and compare the browser-normalised value (`rgb(44, 36, 18)`) against a normalised palette set. String-matching `style="color: #2c2412"` accepts `color: #2c2412; background-image: url(...)`, CSS escapes, and comment-split declarations.
- MUST enforce that `span` carries **only** `style` and nothing else (drop the element's entire attribute set and re-add the one validated colour), and that nesting depth is bounded (a paste can produce thousands of nested spans → preview render stall).
- MUST run the sanitizer on the **paste path inside the editor** as an explicit ProseMirror `transformPastedHTML`, not merely "вставка проходит через тот же фильтр" as an aspiration — Tiptap will otherwise apply its own schema-based paste handling first.

**E2 — consider not hand-rolling this.** [severity: decision for the human]
DOMPurify is ~7 KB gzip with the exact config this needs (`ALLOWED_TAGS: ['p','br','span']`, `ALLOWED_ATTR: ['style']`, plus an `uponSanitizeAttribute` hook enforcing the palette) and has absorbed a decade of bypass reports. The spec's §"Открытые допущения" already worries about a ~150 KB gzip budget with Tiptap at 40–60 KB; 7 KB is inside the noise. Hand-rolled allowlist parsers are the documented origin of most mXSS. Recommend DOMPurify + palette hook, and keep the spec's vitest suite as the contract either way.

**E3 — the sanitizer is now security-critical because the token is in localStorage.** [severity: informational]
v1: plain text, no HTML sink, localStorage token was harmless. v2: user-authored HTML rendered into the DOM + a bearer token in `localStorage` = a complete XSS→token-exfiltration chain. The threat model is still "only she writes, and she is not attacking herself" — pasting from a compromised page is the realistic vector, and it is thin. Conclusion: localStorage remains acceptable, **conditional on E1/E2 being done properly**. If the sanitizer is hand-rolled and thin, move the token to a non-JS-readable place or accept the risk explicitly.
SHOULD: add a Content-Security-Policy meta to `index.html` (`default-src 'self'; connect-src 'self' <worker-origin>; script-src 'self'; object-src 'none'; base-uri 'none'`) — near-free defence in depth, and it also blocks exfiltration to an arbitrary origin even if the sanitizer fails.

### F. Splash screens

**F1 — `apple-touch-startup-image` is still the only mechanism; there is no manifest-driven iOS splash.** [severity: confirms the spec — no change needed]
iOS does not generate splash screens from the manifest; the `apple-touch-startup-image` link tags remain required, one per device resolution × orientation ([Apple forums 733490](https://developer.apple.com/forums/thread/733490), [web.dev enhancements](https://web.dev/learn/pwa/enhancements)). `pwa-asset-generator` is still the standard tool and is the right choice. There are periodic "stopped working" reports (one for iOS 16.4 in the Apple forums thread) that resolve to missing/mismatched resolutions rather than removed support. **No credible evidence that iOS 18/26 dropped support** — but I also found no positive 2026 confirmation, so treat as "verify on the actual device", severity LOW.

**F2 — base-path trap, specific to this repo.** [severity: MED — high probability, easy fix]
This app is served from a GitHub Pages subpath; commit `0a3dc1c` already had to fix `navigate()` for `BASE_URL`. `pwa-asset-generator` emits root-relative `href="/apple-splash-….png"` by default, which 404s under `/journal-calendar/`. MUST: generate with the correct base path (or post-process the emitted tags) and MUST verify the splash images resolve — a 404 splash is silent, you just get a white screen.

**F3 — dark mode variants.** [severity: LOW]
`prefers-color-scheme` in the startup-image `media` query is supported (iOS 13+), light declared first then dark ([pwa-asset-generator#51](https://github.com/elegantapp/pwa-asset-generator/issues/51)). The spec excludes dark theme from v2 — but a device in dark mode with only light-mode media queries can match nothing and show a blank splash. MUST: emit both light and dark variants pointing at the **same** `#fbf6e9` image, so every device matches something. Also note iOS 17 had a bug where PWA colour-scheme changes needed an app restart (fixed in 18) — irrelevant while there is no dark theme, relevant if one is added later.

**F4 — splash images must be precached.** [severity: LOW]
Spec says they go in `public/` and "войдут в precache" — confirm the workbox/vite-pwa glob actually includes them and that adding ~15 PNGs does not blow the precache budget or the SW install time on a slow connection.

## 4. Common Traps in This Domain

- **Trap: treating "empty response" and "failed response" as the same state in an offline-first client.** Every serious offline-sync data-loss story starts here. KV's cached negative lookups (D2) make it a live possibility, not a theoretical one.
- **Trap: read-modify-write on a KV "index" key.** No CAS, eventual consistency, concurrent writers silently lose entries. The index is the single most dangerous key in this system because losing it orphans every entry even though the entry keys survive.
- **Trap: verifying a copy against the key list the copy step produced.** Self-consistent, and blind to exactly the keys you needed it to catch.
- **Trap: assuming `wrangler rollback` restores the environment, not just the code.** Secrets, and bindings, are not rolled back.
- **Trap: `passive: true` default on `touchstart` in Safari** — every "preventDefault didn't work" gesture bug on iOS.
- **Trap: measuring text limits in UTF-16 code units for a non-Latin language.** 2× discrepancy for Cyrillic, and it always shows up as "saving silently fails for long entries".
- **Trap: guarding editor writes on focus instead of composition state.** Focus is neither necessary nor sufficient; `view.composing` is the right predicate.
- **Trap: `click` handlers next to an iOS contenteditable.** See tiptap#7514; `touchend`/`pointerup` is the defensive default on iOS.
- **Trap: root-relative asset paths in a subpath deployment.** Already bit this repo once (commit `0a3dc1c`).
- **Trap: assuming standalone PWA storage carries over from Safari.** It does not, and the first thing lost is the credential.

## 5. Regulatory / Compliance Notes

Low-stakes: a personal diary, two known users, self-hosted on the operator's own Cloudflare account and GitHub Pages, no third parties, no analytics, no processing of others' data.

- **GDPR**: the friend is an identifiable EU/RU-resident data subject and the content is highly sensitive personal data (a diary). No formal obligations attach to a purely personal/household-activity project (GDPR Art. 2(2)(c) household exemption) as long as it is not offered to the public. **This exemption evaporates the moment a third account belongs to someone outside the household** — which the multi-account work in v2 makes structurally easy. Flag for the human: v2 turns a single-user toy into a multi-tenant service, and the compliance posture changes with the third user, not the second.
- **Data minimisation, practical form**: the migration backup (D8) is an unencrypted full copy of a person's diary sitting on a laptop with a documented malware incident. That is the highest-real-risk item in this entire audit from the data subject's point of view, and it is a two-line fix.
- **Right to erasure, practical form**: legacy keys are kept "архивом навсегда" (§1). That is a deliberate, sensible safety decision — but it means "delete my entry" no longer deletes it. Someone should decide (and ideally tell her) that the archive exists and when it gets destroyed. Suggest: destroy legacy keys on a calendar date after Phase C acceptance, not "never".

No PCI/HIPAA/SCA/accessibility-regulation surface. No cookie consent surface (no cookies, no third-party requests).

## 7. Design Constraints for the Plan (non-negotiable)

Auth / worker:
1. MUST implement `verifyToken` with Cloudflare's length-safe pattern (`lengthsMatch ? timingSafeEqual(a,b) : !timingSafeEqual(a,a)`). MUST NOT remove the length check without it — `timingSafeEqual` throws on unequal lengths.
2. MUST parse `JOURNAL_TOKENS` once with validation; malformed secret ⇒ 401 (fail closed), never 500.
3. MUST measure the 64 KB body limit in UTF-8 **bytes** on both client and server using one shared helper.
4. MUST make a 400 from the worker remove the entry from the dirty set and surface a visible error; MUST NOT let a rejected entry retry forever and block the sync queue.
5. MUST keep `JOURNAL_TOKEN` provisioned as a secret for the full rollback window; deleting it is a separate, later change.
6. MUST rehearse deploy → `wrangler rollback` → re-deploy on the test account before touching the friend's data.

Migration:
7. MUST derive the migration key set from the union of `index` and a fully-paginated `list()`, and MUST verify against an independently derived key set with `index.length === copied === verified` asserted.
8. MUST paginate `list()` with cursor + repeated prefix until `list_complete`.
9. MUST allow ≥ 60 s between the last copy write and the deploy, and MUST verify through the **deployed worker**, not the REST API, before declaring success.
10. MUST run the migration in a coordinated quiet window (friend asked not to use the app), or behind a per-account `MIGRATING` flag that returns 503 rather than an empty index.
11. MUST write the KV snapshot outside the repository working tree, and SHOULD encrypt it.
12. MUST make the delta step report-only by default (`--apply` to write) and hard-stop if any destination value is newer than its source.

Client sync:
13. MUST NOT treat an empty/absent index as a completed initial pull. "Namespace initialised" requires an unambiguous success signal.
14. MUST drain the legacy dirty set + legacy Dexie DB into the new namespace on first run before marking it initialised (or, minimum, display the orphaned dates).
15. MUST never rebuild `a:<acct>:index` from a client-supplied full list; index mutations are additive per date.
16. MUST render an explicit "loading, needs network" state when the new namespace is empty and the legacy DB is not — never an empty journal.
17. MUST trigger the namespace switch from client version detection, not from deploy timing (iOS SW activation lags by a cold start).

Editor:
18. MUST guard all programmatic content writes on `editor.view.composing === false`; defer to `compositionend` otherwise. Focus alone is not a sufficient guard.
19. MUST keep the editor's **computed** font-size ≥ 16 px (or use the `scale()` compensation); the line-rhythm recalibration in §4 is constrained by this.
20. MUST bind palette dots and DayView controls to `pointerup`/`touchend`, not `click` (tiptap#7514).
21. MUST use an explicit `transformPastedHTML` hook for the paste path.
22. MUST store an unambiguous plain-text-vs-HTML marker rather than a `<p>`-prefix heuristic.

Gestures:
23. MUST register the pager's `touchstart` with `{ passive: false }` and call `preventDefault()` for touches that begin inside the pager. The 24 px inset alone is not a documented guarantee.
24. MUST state the history push-vs-replace policy explicitly and cap history growth.
25. MUST NOT animate the pager while the keyboard is dismissing; blur, wait for `visualViewport` to settle, then transform.
26. MUST NOT rely on `position: fixed` / `100vh` for the DayView header.

PWA:
27. MUST detect standalone via `navigator.standalone === true || matchMedia('(display-mode: standalone)').matches`.
28. MUST order the gates `install hint → token`, and MUST warn the user the token is entered again inside the installed app (Safari and standalone storage are separate).
29. MUST emit both light and dark `apple-touch-startup-image` variants (same image) and MUST verify the hrefs resolve under the GitHub Pages base path.

Sanitizer:
30. MUST insert sanitized **nodes**, not a serialized HTML string; if a string sink is unavoidable, MUST verify sanitize-twice stability and reject on divergence.
31. MUST validate colours via CSSOM round-trip against a normalised palette, not string matching.
32. MUST drop non-XHTML-namespace elements, comments, `<template>`, `<noscript>`, `<style>`; MUST strip and rebuild `span` attributes; MUST bound nesting depth.
33. SHOULD use DOMPurify + palette hook instead of a hand-rolled parser (~7 KB gzip, inside the stated budget).
34. SHOULD add a CSP meta tag to `index.html`.

## 8. Open Questions for the Human

1. **Does the friend have her token written down anywhere outside her phone?** If not, a storage eviction or an icon deletion locks her out permanently and there is no recovery path in the spec. This should be resolved *before* Phase A, not after.
2. **Is a coordinated migration window acceptable** — i.e. can you ask her to not open the app for ~15 minutes at a known time? Without it, D2 has no clean mitigation and the plan needs the more complex `MIGRATING` 503 flag instead.
3. **DOMPurify or hand-rolled sanitizer?** ~7 KB gzip against a decade of absorbed bypass reports, versus a bespoke module the spec already budgets vitest coverage for. This is a taste/budget call, not a technical one.
4. **Push or replace for swipe navigation history?** Determines whether the iOS system edge-swipe behaves as "previous week" or as a no-op. Product decision.
5. **If tiptap#7514 reproduces on her iOS version**, is "no selection painting, pen-colour-for-subsequent-typing only" an acceptable v2, or does the release wait? Worth deciding now so Phase B has a decision rule instead of a debate.
6. **When (if ever) do the legacy KV keys get destroyed?** "Архивом навсегда" is the safe engineering answer and the wrong privacy answer for a diary. Suggest a calendar date after Phase C.
7. **Will there ever be a third account belonging to someone outside the household?** If yes, the GDPR household exemption stops applying and the posture changes — worth knowing before the multi-tenant plumbing is built to a "just us" standard.
8. **Exact iOS version on her iPhone.** Several findings (B3, C1, F1) are version-sensitive and the Phase C checklist should pin it.
